先把结论说清楚:**工具调用里,模型只产出结构化的调用意图,真正执行的是业务代码。** 模型说"要查库存,参数是 SKU-1024",你的代码去查库、拿结果、把结果回传给模型。密钥、权限、审计全程留在业务侧。

这条边界是工具调用所有设计决策的总纲:模型是不可控的一层,它能做的就是说;可控的一层(你的服务)才配做。

## 一次工具调用的完整循环

```text
1. 你:把可用工具(schema)随请求发给模型
2. 模型:输出调用意图 { name: "query_stock", args: { sku: "SKU-1024" } }
3. 你的代码:校验参数 → 执行 → 拿结果
4. 你的代码:把结果作为新消息回传给模型
5. 模型:基于结果继续生成,或再次发起调用
```

第 3 步是分水岭:**模型从这一刻起就在等,世界里发生的任何事都与它无关**。查库、调支付、发邮件,全在你的代码里发生。模型甚至不知道工具是否执行成功——它看到的只是你回传的那段结果文本。

## 工具怎么描述:给模型看的"说明书"

每个工具用 schema 描述,模型靠这段描述决定何时调、怎么调:

```json
{
  "name": "query_stock",
  "description": "查询指定 SKU 的实时库存。返回剩余数量与在途数量。",
  "parameters": {
    "type": "object",
    "properties": {
      "sku": { "type": "string", "description": "商品编号,如 SKU-1024" }
    },
    "required": ["sku"]
  }
}
```

写法上三条经验:

- **description 写使用场景,不写实现细节**。模型读它来决定"要不要用这个工具",写清"什么时候该用"比"它内部怎么实现"重要。
- **参数名自解释**。`sku` 比 `id` 好,模型填错的概率直接下降。
- **工具数量控制在一屏内**。挂了几十个工具,模型选错的概率随数量上升;按场景分组下发,好过一股脑全挂上。

## 外部工具链:模型能碰什么,不能碰什么

Agent 要接的外部系统,大致三类,接法有共性:

| 类型 | 例子 | 接法要点 |
| --- | --- | --- |
| 数据查询 | 数据库、数仓、向量库 | 业务侧封装受控接口,参数化查询,禁止把 SQL 拼接权交出去 |
| 业务系统 | 订单、工单、审批流 | 复用系统已有的服务接口,幂等键沿用业务单号 |
| 第三方服务 | 支付、短信、地图 | 密钥在服务端,调用限额与超时在代码里设 |

一条红线:**任何系统都不该由模型直连。** 让模型直接写 SQL,等于把注入风险、权限边界、审计能力一起交给不可控的一层。正确做法永远是业务侧封装一个窄接口,模型只配填参数。

## 容错:工程手段,一样都不能少

工具链的稳定性,靠的全是业务代码的基本功:

**参数校验。** 模型输出符合 schema 但语义可能是错的(日期格式对、日期在未来)。校验失败时,把错误信息回传给模型:"参数 date 必须是过去 30 天内的日期",它会修正后重新产出调用意图。模型不会自己重试——重试的循环由你的代码控制。

**超时与退避重试。** 外部服务超时是常态。重试要带指数退避,且要区分错误类型:限流(429)该退避,参数错误(400)重试多少遍都一样。

**幂等。** 超时后重试,最怕创建类接口生效两次——订单重复、邮件重复发送。解法是幂等键:同一业务单号的重复请求只生效一次。模型每次重试带同一个业务号,服务端按单号去重。这是工具调用容错的基本功,也是面试高频题。

**结果裁剪。** 工具一次返回三万行 JSON,原样回传给模型,窗口被撑爆、关键信息被稀释。在工具侧做字段裁剪、分页、摘要,只回传必要部分。

**失败要说话。** 工具挂了,把"库存查询暂时不可用"回传给模型,它会告诉你"这个信息暂时查不到";把异常栈直接塞回去,模型只会复读一段乱码。**错误信息也是上下文,同样要工程化。**

## MCP:把"接工具"标准化

每接一个工具、每换一个模型客户端,都要写一遍适配,这件事被 MCP(Model Context Protocol)标准化了:

- **工具方**按 MCP 协议暴露自己的能力(有哪些工具、参数 schema 是什么);
- **客户端**(IDE、Agent 应用)按协议发现和调用;
- **接入一次,多方可用**。工具开发者接一遍 MCP,所有支持 MCP 的客户端都能直接用。

对应用开发者的实际影响:自研内部工具时,按 MCP 暴露一次,自己的应用、同事的 Agent、测试工具都能复用,适配代码从"N × M"变成"N + M"。

## 面试常问的三个判断

1. **"模型能自己连数据库吗?"** 工程上不应该。模型只配产出调用意图,直连数据库会把注入风险、权限与审计交给不可控的一层。业务侧封装受控接口,模型填参数,代码执行。
2. **"工具调用失败了怎么办?"** 把失败原因回传给模型让它修正重试,重试循环与超时、退避、幂等全在业务代码里。模型不会自己重试。
3. **"密钥放哪?"** 服务端。模型从头到尾没见过密钥,它只传递参数;执行时的鉴权由你的代码完成。

## 一句话记住

**工具调用是模型与真实系统之间的一道受控接口:模型出意图,代码管执行。** schema 描述能力,回传闭环结果,校验/重试/幂等兜住可靠性——可控的那一层,全在你的代码里。
