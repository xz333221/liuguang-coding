先把结论说清楚:**AI 应用的运维与普通 Web 服务同构——容器化、调度、观测、发布,一样不少。** 真正多出来的是三件事:GPU 资源的声明方式、模型版本的灰度策略、以及模型 API 密钥的保管边界。

## 容器化:部署的起点

把应用连同依赖打进一个镜像,解决的是"在我机器上能跑"的问题:环境一致、依赖隔离、随时拉得起、横向扩得动。这一层和普通服务没有区别,做法也通用——多阶段构建压镜像体积、.dockerignore 排除无关文件、基础镜像选精简版。

AI 应用多一个变量:**模型文件放哪**。几十 GB 的权重有三条路:

| 方式 | 做法 | 适合 |
| --- | --- | --- |
| 打进镜像 | 构建时 COPY 进层 | 模型小、发布不频繁 |
| 启动时拉取 | 入口脚本从对象存储下载 | 模型大、多环境复用同一镜像 |
| 存卷挂载 | 模型放在共享存储,运行时挂载 | 多副本共享、模型热更新 |

镜像里塞几十 GB 权重,每次改一行业务代码都要重推整个镜像——这是最常见的浪费。模型与代码分离,是 AI 应用容器化的第一个设计决策。

## K8s:调度、扩缩与自愈

K8s 负责副本调度、故障恢复、滚动发布,它管运行,不替你做技术决策。AI 推理服务在它上面,有三处和普通服务不同:

**资源声明。** GPU 要显式写进 requests(调度依据)和 limits(使用上限)。写少了调度不上、写多了浪费。K8s 不会自己判断"该给这个模型几张卡"——它只按你声明的数字分配。

**健康检查。** 推理服务的启动慢(加载模型要分钟级),readiness 探针要留足启动时间,否则 K8s 会反复把还在加载的 Pod 判死重启。探针端点设计成"模型加载完成才返回 200",是标准做法。

**扩缩容。** 按 CPU 扩缩对推理服务常常失灵——GPU 打满时 CPU 可能还闲着。扩缩指标要看自定义指标:请求队列长度、GPU 利用率、并发数。首 token 延迟飙升而队列排长,是比 CPU 更靠谱的扩容信号。

## 可观测性:看哪些指标

推理服务线上出问题,靠的是指标定位,不是猜。和普通服务重合的部分:延迟分位数(P50/P99)、吞吐(QPS)、错误率、资源利用率。AI 应用特有的几个:

- **首 token 延迟(TTFT)**:用户点发送到看到第一个字的时间,直接体感;
- **吐字速率(tokens/s)**:生成阶段的流畅度;
- **显存占用与 KV 缓存命中率**:容量规划和性能调优的依据;
- **单请求成本**:输入 token 数 × 单价 + 输出 token 数 × 单价,做容量规划和异常检测(某个用户一次请求烧掉几百块,要在成本上看出来);
- **上下文长度分布**:窗口越用越长,成本超线性上涨,这个分布能提前预警。

告警设计上,延迟和错误率之外,**成本突增和上下文长度分布异常值得单独立项**——它们不表现为"服务挂了",表现为账单和用户体感悄悄恶化。

## 发布:模型也是版本

AI 应用的发布比普通应用多一层:**模型本身会变**。换模型、换量化版本、换提示词模板,都算发布。灰度手段与普通服务一致,对象要覆盖全:

- **按流量比例切分**:5% 流量走新模型,对比延迟、错误率、成本、用户反馈指标;
- **一键回滚**:指标异常切回旧版,切的是代码 + 模型版本 + 提示词版本这一整套;
- **提示词也进版本管理**:提示词是行为的一部分,改提示词和改代码一样要评审、要灰度、要能回滚。

只灰度代码不灰度模型,是新版模型全量上线后才发现效果退化,回滚时连提示词带模型一起抓瞎。

## 密钥与边界

最后一条红线,面试里出现频率极高:**API 密钥不进前端代码。** 前端代码对所有用户可见,压缩混淆只是提高门槛,不是安全。密钥留在服务端,浏览器只持有访问你自己服务的权限。

顺着这条线,模型调用应该经过自己的后端中转——顺带获得三样东西:密钥不暴露、调用可审计(谁在什么时候用了多少 token)、可限流熔断。模型 API 直连前端的应用,等于把账单和滥用风险一起敞开。

## 面试常问的三个判断

1. **"K8s 能自动决定推理用几张卡吗?"** 它按你声明的 requests/limits 调度。判断"该用几张卡"是你的决策(模型大小、并发、延迟要求),不是 K8s 的。
2. **"推理服务重点盯什么指标?"** 延迟分位数、首 token 延迟、吐字速率、吞吐、错误率、显存、单请求成本。只有准确率是不够的——准确率靠离线评测集,线上靠这些指标。
3. **"密钥写在前端,混淆过就行吗?"** 混淆对所有用户可见的代码只是门槛。密钥必须留在服务端,前端只访问自己的后端接口。

## 一句话记住

**AI 应用运维与普通服务同构,多出来的是三件事:GPU 资源显式声明、模型与提示词一起灰度、密钥只在服务端。** 模型和代码分离部署,按队列长度和 GPU 利用率扩缩,盯住首 token 延迟与单请求成本——服务稳不稳,靠的是这些工程细节,不是模型本身。
