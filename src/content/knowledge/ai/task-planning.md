先把结论说清楚:**Agent 是一个"想一步、做一步"的循环。** 模型负责规划和判断,工具负责执行,观察结果回传给模型决定下一步。单次问答是模型生成一段文字;Agent 是模型带着目标,在一圈圈循环里把任务做完。

## 循环长什么样

ReAct 是最基础的 Agent 范式,一次循环三步:

```text
目标:查一下 SKU-1024 的库存,有货就下单,没货给替代建议

Thought:我需要先查库存 → Action:query_stock(SKU-1024)
Observation:剩余 3 件
Thought:有货,可以下单 → Action:create_order(SKU-1024, 数量 1)
Observation:订单创建成功,单号 SO-2026-1015
Thought:任务完成 → 回答用户
```

"想"和"做"交替进行,每一步的观察成为下一步推理的输入。**这个循环结构,比任何提示词技巧都更接近"Agent"的本质**——模型不再是一次性生成答案,而是在与环境交互中推进任务。

## 任务规划:拆多细

把目标拆成步骤,粒度是第一个设计决策:

- **拆得太细**:步骤一多,上下文跟着涨,每步传递都有信息损耗,误差逐层累积。五步能干完的事拆成二十步,往往是步数越多错得越远。
- **拆得太粗**:一个步骤里塞进多个决策,中间没法检查,错了整步重来。

实用的判断标准是两条:**需要外部信息的,单独成步**(查库存、查文档);**能本地算完的,合并处理**(算总价、拼文案)。按"信息依赖"和"可验证性"切,而不是按步数切。

## 两种执行节奏

**先出完整计划,再逐步执行。** 适合步骤相对确定的任务:步骤事先能列全,中间结果不会改变路线。好处是计划可审查、可向用户展示;风险是计划定死后,中间出现意外(查到一半发现没货)时容易失效。

**边观察边规划。** 每一步都根据上一步的结果重新决定下一步,ReAct 就是这个节奏。适合步骤强依赖中间结果的开放式任务;风险是方向容易漂,需要额外的终止判断。

工程上的常见组合:**先出粗计划(让用户确认方向),执行中按观察动态调整**。计划管边界,循环管应变。

## 反思:让模型检查自己

反思机制把"评估"也变成一次模型调用:模型检查自己上一步的输出,再决定修正还是继续。

```text
生成初稿 → 模型自评(对照要求逐条检查)→ 发现问题 → 修正 → 再评
```

适用场景很明确:输出质量要求高、错误可检测的任务(代码、文案、数据核对)。代价同样明确:**每一轮反思都是额外调用**,延迟和成本随反思轮数线性上涨。配一个重试上限(常见 2 到 3 轮),避免在"永远不满意"的任务上烧钱。

## 可靠性:工程手段,不是模型能力

Agent 出问题,常见三种形态,各有各的工程解法:

**跑偏停不下来。** 第一步理解错目标,后面每一步都在错误的前提上越跑越远。解法:给循环设**步数上限**;每步设**检查点**(关键动作前暂停,让人或规则确认);**终止条件写死**(目标达成、明确失败、达到上限,三者满足其一就收尾)。

**误差累积。** 每步 95% 的可靠率,十步连乘只剩六成。解法:缩短单步的信息跨度(步与步之间传结构化结果,不传大段自然语言);关键步骤加可自动执行的校验(下单前查库存、发货前验地址)。

**成本失控。** 开放式任务里 Agent 可能空转几十轮。解法:预算上限(最大轮数、最大 token);每轮记录观察摘要,不让原始观察无限堆积;超预算走降级路径(交给人处理,或给出部分结果)。

**这三件事——终止条件、检查点、预算——是 Agent 生产可用与demo可看的差别。** 面试聊 Agent,能主动讲到兜底设计,比多背几个框架名字加分。

## 什么时候别上 Agent

不是所有任务都值得套循环。三条判断:

- **流程确定的,写成固定编排**。"查库存 → 判断 → 下单"用 if-else 或工作流表达,比让模型每次重新决策稳得多,也便宜得多。
- **一步能答的,直接生成**。分类、抽取、改写这类单步任务,套 Agent 循环是纯浪费。
- **错误代价高的,加人工确认**。支付、删除、对外发送,关键动作前留人工审批节点。

行业里有个逐渐成为共识的经验:**从最简单的编排做起,按需增加复杂度**。单次调用够用就别上循环,固定流程够用就别让模型自由规划。

## 一句话记住

**Agent 是把"想一步、做一步"跑成循环:规划定方向,工具出结果,观察驱动下一步。** 而可靠性的来源不是模型多聪明,是终止条件、检查点、预算上限和人工兜底这些工程约束。
