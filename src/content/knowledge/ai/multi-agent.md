先把结论说清楚:**多智能体把任务拆给多个有角色的 Agent,价值在分工与上下文隔离**——每个 Agent 只带自己那部分上下文,提示和工具按职责定制。代价同样明确:多一次信息传递就多一次损耗,多一个出错面。

拆不拆的判断标准只有一条:**职责与上下文确实需要隔离时,才拆。** 简单任务上,单 Agent 通常更稳、更便宜、也更好查错。

## 单 Agent 到瓶颈在哪

单 Agent 一个循环打天下,任务变复杂后会撞上三堵墙:

- **上下文混杂**。规划、检索、写作、校对全在一个窗口里,互相干扰——写作用的例子把检索步骤的判断带偏,是常见现象。
- **提示互相拉扯**。一个 system 提示既要它严谨查证,又要它文采飞扬,两种要求在同一段上下文里打架。
- **工具全量挂载**。十几种工具挂在一个 Agent 上,选错工具的概率随数量上升。

多 Agent 的思路就是把这些切开:每个 Agent 一段精简的 system、一套专属工具、一个独立窗口。

## 两种协作模式

**编排模式(中心化)。** 一个编排者负责分派与汇总,工作者各干各的:

```text
用户请求
   ↓
编排者:拆解 → 分派任务 A / B / C
   ↓
工作者A(检索) 工作者B(分析) 工作者C(写作)
   ↓
编排者:汇总 → 检查 → 交付
```

谁接手、何时收尾都由编排者决定,流程收得住。Anthropic 的多 Agent 研究系统就是这个结构,公开复盘里提到关键收益是上下文隔离:每个子 Agent 只处理自己那一份资料,主线程不被细节淹没。

**自主协商(去中心化)。** 多个角色通过对话协议自己推进,AutoGen 是这一路的代表:角色之间按约定好的对话规则轮流发言,直到达成终止条件。灵活,也最难控——没有中枢,任务容易在角色之间来回踢皮球。

生产环境的经验偏向很明确:**要可控,选编排;要探索性的开放讨论,才考虑自主协商**,且必须配硬终止条件。

## 拆完之后的新问题

每个多 Agent 系统都要回答四个问题,答不上来就会在演示里翻车:

**1. 消息怎么传。** Agent 之间靠结构化消息交换,不靠自然语言闲聊。消息要带版本、带类型(任务 / 结果 / 失败),口径在传递中慢慢漂移是多 Agent 最常见的慢性病——A 说的"库存"和 B 理解的"库存"对不上,错到最后都查不出源头。

**2. 责任怎么分。** 每个任务有且只有一个责任 Agent。两个 Agent 都能干同一件事,结果是互相等待或重复劳动。

**3. 什么时候停。** 协作流程必须有终止条件:任务完成、明确失败、达到轮数上限,三者满足其一即收尾。没有终止条件的多 Agent,互相触发会形成无限循环——两个 Agent 互相请求对方补充信息,跑到天荒地老。

**4. 错了怎么查。** 单 Agent 出错,看一段日志;五个 Agent 出错,要能把一次失败归因到具体某个 Agent 的某一步。链路追踪(每步记录 Agent、输入、输出、耗时)从第一天就要有,事后补不出来。

## 框架给的与框架不给的

AutoGen、MetaGPT 这类框架,把"多个有角色的模型实例怎么对话与交接"做成了基础设施:对话协议、角色管理、终止判断都有现成实现。开发者写角色和流程,不用从零搭消息机制。

但要清楚框架**不给**的东西:任务拆解的合理性、终止条件的严格程度、消息 schema 的设计——这些恰恰是多 Agent 系统质量的真正来源。框架解决"怎么说话",不解决"说什么、何时闭嘴"。

选型上两者的差异值得记住:AutoGen 偏对话协议, MetaGPT 偏角色化流程(把软件公司的 SOP 形式化:产品经理写文档、架构师出设计、工程师写代码)。抽象层次不同,要的可控性不同,选择就不同。

## 面试常问的三个判断

1. **"Agent 越多越好吗?"** 每多一个 Agent,多一次传递损耗、多一个出错面。简单任务上单 Agent 更稳;职责与上下文确实需要隔离时才拆。
2. **"多 Agent 能突破上下文窗口吗?"** 每个 Agent 的窗口照旧受限,多 Agent 做的是把任务切成适配窗口的块,窗口本身没有变大。
3. **"两个 Agent 循环对话停不下来,怎么办?"** 补终止条件与责任边界:轮数上限、完成判定、一个明确的仲裁角色。没有边界的互相触发必然空转。

## 一句话记住

**多智能体的收益是分工与上下文隔离,成本是通信损耗与编排复杂度。** 拆之前先问"确实需要隔离吗";拆之后守住四件事:结构化消息、单一责任、硬终止条件、全程可追踪。
