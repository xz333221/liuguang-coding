上一篇结束时,DOM 与 CSSOM 已经各自建好,但屏幕上还什么都没有。这一篇接着往下走:样式怎么落到每个元素上,盒子怎么排进页面,像素由哪一步产生,以及主线程与合成线程在同一帧里各做什么。

## 两棵树合并之后

DOM 提供结构,CSSOM 提供规则。渲染的第一步是把两者对上:从根节点向下遍历,为每个元素匹配规则、做层叠与继承,得到计算样式(computed style)。这一步在规范里叫 style,在 DevTools 里叫 Recalculate Style。

只保留会生成盒子的节点,得到的树叫布局树(layout tree,旧称 render tree)。规则有几条:

- `display: none` 的元素及其子树不进入布局树;
- `visibility: hidden` 的元素进入布局树,占位置,但不绘制;
- `::before`、`::after` 会作为独立盒子进入;
- 纯文本节点被包成匿名行内盒。

```text
DOM + CSSOM
    │  style:匹配规则、层叠、继承
    ▼
布局树(可见元素与盒子)
    │  layout:计算位置与尺寸
    ▼
盒子几何(x / y / width / height)
    │  paint:生成绘制指令
    ▼
绘制记录(按顺序的填充、描边、文字、图片)
    │  raster:光栅化
    ▼
瓦片位图
    │  composite:按层拼合
    ▼
屏幕上的一帧
```

五个阶段里,前三个在主线程,光栅化在光栅线程与 GPU 上,合成在合成线程。分工是后面所有性能讨论的基础。

## 样式计算的开销

每新增或修改一个元素,浏览器都要为它匹配规则。匹配从选择器最右侧开始向左回溯:`.list .item a` 先找出所有 `a`,再检查祖先里有没有 `.item` 与 `.list`。右侧越具体,候选集越小,回溯越短。

```css
/* 候选集是所有 span,再逐层回溯祖先 */
.list div span { color: #666; }

/* 候选集是带这个类的元素,一次命中 */
.item-title { color: #666; }
```

两条规则都能用,但第一条在节点多时更容易变慢,还更难覆盖。工程上通常用单个类名表达样式,选择器层级压到一层。

改动的范围也影响开销。给根元素换一个类,整棵树的计算样式都可能失效;改一个叶子节点的颜色,只重算它自己。用 CSS 变量时同理:在 `:root` 上改一个被大量元素继承的变量,所有使用者都要重算,而在局部容器上改变量,影响就限于该子树。

一个常见的错误写法是用 JS 每帧修改 `:root` 上的变量来驱动动画。变量被全站继承,每帧都要让成千上万个元素重算样式,主线程很快被占满。这类动画应该改成对目标元素做 `transform`,或者至少把变量声明在动画所在的容器上,把重算范围收窄。

## 布局:盒子落到坐标上

布局的输入是布局树与视口尺寸,输出是每个盒子的位置与大小。相对单位在这一步解析:`width: 50%`、`1.5rem`、`auto` 都要结合包含块算出具体像素。

布局是自上而下传约束、自下而上回报尺寸的过程。父元素先给可用宽度,子元素算出自己的高度,父元素再决定自己的高度。因此子元素变高会向上影响父元素,再影响后面的兄弟,一次改动可能波及一整条链。

不同布局方式的代价不一样:

- 常规流:按顺序排版,局部改动通常只影响后续兄弟;
- 绝对定位与固定定位:脱离常规流,变化不影响其它元素的位置;
- 表格:列宽由整列内容决定,改一个单元格可能触发整表重算;
- 网格与多列:需要参考整体轨道或列高,局部改动的影响面比常规流大。

布局在英文里叫 layout,Firefox 的旧术语是 reflow,中文习惯叫重排。两者指同一件事。

## 绘制:先产出指令

布局完成后,浏览器遍历布局树,生成绘制指令(paint records,也叫 display list)。这一步只记录「画什么、按什么顺序画」,还没有任何像素。

单个盒子的绘制顺序大致是:

```text
背景色 → 背景图 → 边框 → 内容(文字、图片) → 轮廓 → 子元素
```

绘制会按层叠上下文拆成若干块,便于后续单独重绘。一个元素变色时,浏览器只需重画它所在的那一块,不必重画整页。

要注意绘制与光栅化的区别。绘制是主线程上的遍历,产出的是指令;把指令变成像素是光栅化(raster),发生在其后的阶段,由光栅线程与 GPU 承担。DevTools 里的 Paint 耗时指的是前者。

## 光栅化与合成

页面被切成瓦片(tile),光栅线程并行处理视口内及其附近的瓦片。滚动时新进入视口的瓦片才需要光栅化,已经处理过的直接复用。

合成(composite)由合成线程完成:它持有层树(layer tree),把各层的瓦片按变换与透明度拼成一张图,交给显示合成器上屏。合成线程不执行 JS,也不做布局,所以它能独立于主线程推进滚动与 `transform` 动画。

| 阶段 | 执行者 | 主要输入 | 产出 |
| --- | --- | --- | --- |
| 样式计算 | 主线程 | DOM、CSSOM | 每个元素的计算样式 |
| 布局 | 主线程 | 计算样式、视口 | 盒子几何 |
| 绘制 | 主线程 | 几何、样式 | 绘制指令列表 |
| 光栅化 | 光栅线程、GPU | 绘制指令 | 瓦片位图 |
| 合成 | 合成线程 | 层树、瓦片 | 一帧画面 |

这张表解释了很多现象:主线程被长任务占住时,样式与布局排不上队,但合成线程仍能把已有的层滚动起来,于是页面「能滚但卡住不动」;反过来,层没有提升时,`transform` 动画仍要主线程每帧重绘。

## 一帧的时间预算

60Hz 屏幕每 16.7ms 刷新一次,120Hz 是 8.3ms。浏览器自己还要处理输入、跑 rAF 回调、检查微任务,留给脚本与渲染的时间比这个数更少。

```text
输入事件 → rAF 回调 → 样式 → 布局 → 绘制 → 光栅化 → 合成 → 上屏
```

一次 50ms 的同步任务会让三帧直接跳过,用户看到的就是卡顿。把长任务拆小,或者挪进 Worker,是保住帧率的前提。

一个具体的坑:给进度条做动画时改 `width`,每一帧都要重新布局、重绘整条,主线程稍有占用就掉帧;改成 `transform: scaleX()` 并配合 `transform-origin: left`,只改变合成层的矩阵,布局与绘制都不参与。下一篇《重排、重绘与合成层》里,这几种代价的差别就是主线。

```js
function loop(now) {
  // 只写不读,避免在读的时候强制刷新布局
  box.style.transform = `translateX(${Math.min(now / 10, 300)}px)`;
  requestAnimationFrame(loop);
}
requestAnimationFrame(loop);
```

这段动画每帧只改 `transform`,元素被提升为合成层后,主线程没有布局与绘制工作,合成线程按新矩阵重绘这一层即可。

## 在 DevTools 里看流水线

- Performance 面板录制后,主线程轨道上能看到 Recalculate Style、Layout、Paint 的耗时块;
- Rendering 面板打开 Paint flashing,重绘区域会被高亮;
- Layers 面板列出合成层,Layer borders 显示层的边界;
- FPS meter 观察帧率与 GPU 内存。

判断方法很直接:有 Layout 块,说明几何变了;只有 Paint,说明只改了外观;两者都没有、只剩 Composite Layers,说明改动交给了合成线程。先看哪一段最长,再决定改属性还是改结构。

## 小结

- 渲染从样式计算开始,只有可见元素进入布局树;
- 布局把相对尺寸解析成像素,父子尺寸互相牵制;
- 绘制产出指令列表,像素在光栅化阶段才产生;
- 光栅化在光栅线程与 GPU 上执行,合成在合成线程完成;
- 样式、布局、绘制占主线程,长任务会直接拖低帧率;
- Performance、Rendering、Layers 三个面板分别对应流水线的不同段。
