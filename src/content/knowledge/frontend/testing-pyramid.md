上一篇用 Lighthouse、Performance 面板与 RUM 量出了页面慢在哪。数字只指出症状，把那段代码改掉才是动作；而每改一次就得回归一遍，人工点一遍要半天，漏掉的概率还不低。测试是把这份回归成本摊平的东西，只是三层的价格差着几个数量级，先得分清各自买到了什么。

## 三类测试各自替换了什么

单元测试只测一个函数或一个模块，网络、DOM、时间全换成替身。组件测试把组件渲染进 jsdom 或 happy-dom，点按钮、填表单，断言屏幕上出现了什么。端到端测试开一个真浏览器，从输入地址走完整条路径。

| 层级 | 替换掉什么 | 单次耗时 | 一个用例的维护成本 | 失败时看得到 |
| --- | --- | --- | --- | --- |
| 单元 | 网络、DOM、时钟全部替身 | 毫秒以内 | 低，逻辑变了才改 | 具体哪个函数、哪一行 |
| 组件 | 网络替身，DOM 是真的 | 几十毫秒 | 中，交互变了要改 | 哪个组件、哪个操作 |
| 端到端 | 什么都不换 | 秒级起 | 高，流程变了要重写 | 一张截图和一段录制 |

覆盖范围是反过来的。单元测试跑一百条，也只覆盖一百个函数；一条端到端能顺路穿过路由、鉴权、接口与渲染。所以两者的取舍不是「哪个更好」，是拿多少确定性换多少覆盖面。

## 为什么越往上越少

端到端不稳定的来源太多： 网络抖动、动画没结束就点击、第三方脚本延迟、测试数据被另一条用例改掉。一条 E2E 红了你拿到的是「点了支付之后没出现成功页」，得回放 trace 才知道是前端没发请求，还是后端返回了 500，还是提示文案改了。

```text
       /\        端到端    主路径:登录、下单、支付
      /  \
     /    \      组件测试  表单校验、列表渲染、空态与错误态
    /      \
   /--------\    单元测试  计算、转换、校验规则、状态迁移
```

比例没有硬指标。常见的一个起点是单元测试几十到几百条，组件测试覆盖主要交互，端到端留 5 到 15 条主流程。数字本身没意义，被覆盖的风险才有。

反过来的形状叫冰淇淋筒： 大量手工测试加一堆端到端，单元测试几乎没有。表现是一轮全量跑二十分钟，红了三条没人愿意查，最后统一加 `retries` 让它们偶尔变绿。

判断一条用例该放哪一层，问三个问题就够了：

- 出错时，我希望测试告诉我是哪一行，还是只告诉我是哪一步？
- 这个行为依赖真实的浏览器布局、路由或跨域吗？
- 它多久会变一次？变得越勤，越该用便宜的测试兜住。

三个答案的组合基本就定层了。一个金额计算的边界条件，希望精确到行、不依赖浏览器、逻辑稳定，就该落到单元测试。一个「登录失败三次锁定账号」的提示，依赖真实会话与后端状态，只能端到端验证。

## 手工测试仍然要做

自动化不能替代人。第一次用某个功能的人和写它的人，看到的东西完全不同： 按钮点下去没反应但没报错、文案有歧义、错误提示出现在屏幕外面、加载态一闪而过。这些没法写成断言，只能靠探索性测试。

合理的分工是： 每次提交跑自动化，挡住已知的回归； 每个迭代花半小时，按真实路径点一遍主流程，专门找「意料之外」。发布前再用真实设备过一遍： 移动端的手势、键盘弹起顶起布局、系统字号调大之后的截断，模拟器都还原不了。

## 测试写在行为上

这条决定了测试是资产还是负债。断言内部实现，重构一次要改一批测试；断言外部行为，换实现不用动测试。

```js
// 反例:断言内部调了哪个方法
test('结算', () => {
  const cart = new Cart([{ price: 100, qty: 2 }])
  const spy = vi.spyOn(cart, 'recalculateTax')
  cart.checkout()
  expect(spy).toHaveBeenCalledTimes(1)
})

// 正例:断言调用方能观察到的结果
test('结算', () => {
  const cart = new Cart([{ price: 100, qty: 2 }])
  cart.checkout()
  expect(cart.total).toBe(220)   // 含 10% 税
})
```

第二个版本读代码时能直接看懂业务规则，第一个只证明「这个方法被调用过」。把 `recalculateTax` 内联进 `checkout` 是一次无害的重构，反例会红。

判断标准很朴素： 测试里出现的方法名、类名、调用次数，是不是用户或调用方真正关心的。不是，就删掉这类断言。

粒度同样重要。一条用例只验证一个行为，失败了就知道是哪条规则破了；把「下单、支付、发货」塞进一个 `it`，红了只能整段排查。但拆得太细也不行： 一条用例只断言一个字符是否渲染，改一次文案要改五条。

一个可操作的尺度： 用例的名字能写成一个完整的句子，「数量为负时抛错」「满三件打九折」，一句话说不完就该拆。

## 不值得写测试的部分

- 框架保证的事： React 会不会把 props 传下去、Vue 的响应式会不会触发重渲染，这些是框架自己的测试该管的；
- 纯样式： 颜色、间距、圆角。这类适合截图比对，不适合断言 CSS 属性，见第 16 章讲可访问性测试那篇；
- 第三方库： 你测的是别人的实现，升级时还得跟着改；
- 常量表与纯 getter: 只是把字面量再抄一遍；
- 一次性的迁移脚本与实验代码： 生命周期比写测试的时间还短；
- 马上要删的旧逻辑： 给它补测试等于给死人做体检。

反过来说，最该写的几类： 和钱有关的计算、权限判断、日期与时区、表单校验规则、外部数据的解析、状态机迁移。这些地方错了损失最大，也最好用单元测试表达清楚。

还有一类容易被忽略： 修 bug 之前先写的那条用例。它能把「这个 bug 确实存在」变成一次红灯，修完之后变成绿灯，顺便守住以后不再犯。这条用例的成本几乎为零，信息量比事后补十条都大。

顺序上也有讲究： 先补一条能复现的用例，再动代码。直接改代码去试，改对了不知道为什么对，改错了还得回滚。

## 一条坏测试比没有更贵

测试会腐化。最初的断言被改成 `expect(res).toBeTruthy()`，失败时有人加 `.skip`，红灯挂三天没人管。这时它已经不起保护作用，却还在消耗运行时间和信任。

```js
// 腐化的三步
expect(invoice.total).toBe(220)      // 有效断言
expect(invoice.total).toBeDefined()  // 有人嫌它总失败
expect(invoice).toBeTruthy()         // 再退一步,只证明没返回 null
```

判断一条测试值不值得留： 把它删掉，有没有可能上线一个 bug 而没人发现。答不上来就删。同一条标准也适用于「为了凑覆盖率」写出来的用例。

## 几个常见的坑

- 用覆盖率当目标： 为了让数字好看去补测试，写出来的都是「调用一下不断言」。这个指标怎么骗人，第 16 章讲 CI 门禁那篇展开。
- 端到端覆盖分支： 把「会员折扣有 6 档」写成 6 条 E2E，跑一轮十几分钟。同一件事在单元测试里是 6 行 `it.each`。
- 用例之间共享状态： 上一条往库里写了一条记录，下一条依赖它存在。单独跑绿，全量跑红，顺序一变结果就变。
- 只测成功路径： 每个函数只有「正常输入返回正常结果」，错误分支一条没有，线上第一个异常就打穿。
- 测试和服务端逻辑抢活： 前端单元测试里重算一遍后端返回的金额，两边规则一改就对着红。校验规则该由拥有它的那层测。
- 只测「有没有」不测「对不对」: 断言 `expect(list.length).toBeGreaterThan(0)`，十条数据里九条错也照样绿。

## 小结

- 单元测逻辑，组件测交互，端到端测那条真正走得通的路径，数量往上递减；
- 越往上越慢越脆，失败定位也越模糊，能下沉一层的就别放上面；
- 断言行为不断言实现，测试里的方法名要经得起重构；
- 框架保证的、纯样式的、第三方库的，不值得写测试；
- 涉及钱、权限、时区、校验规则的地方最该有测试；
- 一条只证明「没抛异常」的测试比没有更贵，该删就删。
