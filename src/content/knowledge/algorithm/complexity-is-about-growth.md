先把结论说清楚:**O 记号回答的不是"这段代码跑多少秒"，而是"输入变大时，工作量怎么涨"。** 换台机器、换个语言，秒数会变，增长率不会变。这就是它能跨环境比较两种做法的原因。

## 计时为什么靠不住

最直接的想法是跑一遍计时。但同一个函数，今天的数字和明天对不上:

- CPU 快慢、内存带宽、机器负载都不一样;
- 语言与实现不同:同一段逻辑，Python 解释执行和 C 编译执行能差上百倍;
- 输入数据本身的分布也可能让快慢翻来覆去。

计时测的是"这一次、这台机器"，而不是"这个做法"。我们要的尺子得把机器因素剥掉，只留下随规模变化的那部分。

## 数的是基本操作次数

做法很朴素:把代码里最耗时的那个动作挑出来，数它在最坏情况下要执行多少次。

```python
def find_max(nums):
    best = nums[0]          # 1 次赋值
    for x in nums:          # 循环 n 次
        if x > best:        # 每次 1 次比较
            best = x        # 最多再 n 次赋值
    return best
```

一共大约 `1 + n + n + n` 次操作。接下来两步化简:

1. **丢掉常数因子**。`3n + 1` 里那个 3 只是"每次循环干三件事"，它不随 n 变化，抹掉。
2. **只留最高阶项**。`n + 1` 里，当 n 很大时 "+1" 无足轻重，抹掉。

最后剩下 `n`，写成 **O(n)**。读作"n 的阶"或者口语里的"线性复杂度"。

这套化简在数学上是"取渐近上界":存在常数 c 和一个够大的 n₀，使得操作次数永远不超过 `c · f(n)`。所以 O(f(n)) 只是一个**上界**，不是说"恰好等于 f(n) 次"。

## 三种情况:最好、最坏、平均

看一个查找函数:

```python
def index_of(nums, target):
    for i, x in enumerate(nums):
        if x == target:
            return i
    return -1
```

同一个函数，次数完全看运气:

- **最好**:目标就在第一个，1 次比较，O(1);
- **最坏**:目标在最后，或者根本不在，要看完 n 个，O(n);
- **平均**:目标等概率出现在任意位置，平均看 n/2 个，仍是 O(n)。

日常说"这个算法是 O(n)"，默认指的是**最坏情况**，因为它是对使用者的承诺:再糟也不会超过这个量级。要特别强调时，就说"最坏 O(n)、平均 O(1)"，比如哈希表查找。

## 一张表看增长

把 n 代进去，不同量级之间的差距比想象中大得多:

| 复杂度 | n = 10 | n = 1000 | n = 10⁶ |
| --- | --- | --- | --- |
| O(1) | 1 | 1 | 1 |
| O(log n) | 3 | 10 | 20 |
| O(n) | 10 | 1 000 | 1 000 000 |
| O(n log n) | 33 | 9 966 | 20 000 000 |
| O(n²) | 100 | 1 000 000 | 10¹² |

（对数以 2 为底，取整数近似。）

注意最后一列:`n = 10⁶` 时 O(n²) 是 10¹² 次操作。一台机器每秒大概能做 10⁸ 次简单操作，量级上要跑**一万秒**，也就是几个小时。而 O(n log n) 只要两千万次，零点几秒。

这里有个实用的换算:把每秒约 10⁸ 次简单操作当作粗尺子，先估出操作次数的量级，就能判断"这个方案扛不扛得住"。

## 对数是怎么来的:二分查找

O(log n) 不像 O(n) 那么直观，看一遍就明白:

```python
def bisect(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
```

前提是 `nums` 已经有序。每次比较之后，候选区间**减半**:1000 个数看一眼剩下 500 个，再看一眼剩 250 个……

减半多少次能到 1 个？就是求 2 的多少次方等于 n，也就是 log₂n。所以 100 万个数最多比较约 20 次。这就是 O(log n) 的来处:不是"比线性的快一点"，而是"每多一倍数据才多花一步"。

## O 不等于 Θ

严格说，记号有三兄弟:

- **O(f(n))**:上界，不超过 f(n) 的量级;
- **Ω(f(n))**:下界，至少是 f(n) 的量级;
- **Θ(f(n))**:上下界一致，也就是"恰好是这个量级"。

口语里说"这个算法是 O(n log n)"，心里想的往往是 Θ(n log n)，即"它就这么快"。写论文或做题时两边都得交代清楚，日常讨论不必较真，"最坏 O(…) 平均 O(…)"说全就够了。

## 空间复杂度是另一根轴

时间复杂度量的是"花多少时间"，空间复杂度量的是"额外占多少内存"，数法完全一样:看额外申请的空间随输入怎么涨。

- 原地排序（比如堆排序）额外空间 O(1);
- 归并排序要开一个和输入等大的辅助数组，O(n);
- 递归写法还要把调用栈算进去，递归深度 n 的写法就是 O(n) 的栈空间。

## 常数因子什么时候真的重要

O 只比增长率，所以"O(1) 一定比 O(n) 快"是错的:

- 哈希表查找平均 O(1)，但它要先算哈希、再处理冲突，一次可能比数组按下标取值慢几十倍。只是数据一多，这个固定开销就被摊平了。
- 数据量小的时候，常数小的简单做法常胜出。几十个元素的数组上，插入排序往往比快排还快，所以很多标准库的快排在子区间变短时会切换成插入排序。

**先看数据规模，再谈复杂度。** 规模小到几十，挑最好写、最好懂的那个就行。

## 怎么用这把尺子

1. **看清数据规模**:n 是几十、几万，还是上亿？规模决定了选谁。
2. **写出增长率**:把每层循环、每次递归的次数乘出来，只留最高阶项。
3. **估一下够不够**:按每秒 10⁸ 次粗算，10⁸ 以内是毫秒级，10¹² 量级基本别想。
4. **拿不准就测**:小数据量下实测最快的那版，可能才是该用的那版。

## 四个常见误解

1. **"O(1) 就是快"**。它只是"不随 n 涨"，不代表单次开销小。哈希、缓存未命中、分支预测，都能让 O(1) 的一步比想象中贵。
2. **"看到双重循环就是 O(n²)"**。内层循环不一定跑满 n 次。二分查找外层看着是循环，每次砍一半，是 O(log n)。
3. **"复杂度一样，怎么写都行"**。同一个 O(n log n)，常数差几倍很常见，工程里还是要挑实现。
4. **"复杂度能算出秒数"**。它只给量级。要知道具体耗时，输入真实数据测一遍。

## 一句话总结

**复杂度量的是增长的形状，不是跑分。** 数基本操作、丢掉常数和低阶项，先看数据规模再选做法，就能在还没写代码时判断出哪个方案会先撑不住。
