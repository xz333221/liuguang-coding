上一章在设计模式层面打转，都是「几个类之间怎么配合」。这一章换到系统尺度：一个业务系统几十万行代码，规则互相纠缠，改一个字段要开三次会。DDD 处理的是这个问题，而它的第一件事不是写代码，是划线。

## 一个模型覆盖全系统的代价

设想电商系统里有一个 `Order` 类。销售部门关心：优惠券、支付状态、退款。仓储部门关心：拣货单、库位、发货批次。财务部门关心：开票金额、税率、对账状态。

如果所有人都往同一个 `Order` 上加字段，结果一定是：80 个字段、一半永远为 null、每次改动都影响所有人、没人敢删任何字段。这个类还有个更隐蔽的问题：**同一个词在不同语境下含义不同**。「订单已确认」在销售那里是「客户付款成功」，在仓储那里是「已生成拣货任务」。一个 `status` 字段装不下两个含义，于是有人加 `status2`。

业务复杂度消不掉，但可以**隔离**。把系统按「术语含义一致」切成若干块，每块内部一个模型，这就是限界上下文。

## 统一语言：说一样的话

一个上下文内部，业务和代码用同一套词：

- 业务说「挂账」，代码里就有 `CreditAccount.suspend()`，不叫 `setStatus(3)`;
- 术语表里写清这个词的唯一含义、边界、反例；
- 说话、写文档、写代码、写测试，用同一个词。

听起来像形式主义，实际收益很直接：需求评审时不会出现「你说的下单是指创建订单还是支付完成」这种半小时的扯皮；看代码时不需要在脑子里做一次翻译。

歧义被发现时，**记进术语表并统一**，而不是在代码里各写一套。术语表本身就是这个上下文的边界说明。

## 怎么划边界

三种可操作的划法，通常混用：

1. **按业务能力**。下单、库存、结算、配送，各自是一个能力，天然对应一个上下文；
2. **按团队边界**。康威定律的反向利用：一个团队维护一个上下文，沟通成本最低。跨团队的「共享模型」几乎必然腐化；
3. **按语言变化点**。同一个词的含义在哪里变了，边界就画在哪里。「商品」在销售上下文里是「可售 SKU + 价格」，在仓储上下文里是「体积重量 + 库位」，这就是两个上下文。

判断边界画得对不对，有个简单的检验：**这个上下文能不能独立改一次需求而不惊动别人**。如果每次改动都要同步改三个服务，边界就画错了。

## 上下文之间怎么协作

切完之后必须通信，DDD 总结了五种关系，常用的四种：

| 关系 | 含义 | 适用 |
| --- | --- | --- |
| 共享内核 | 两个上下文共用一小块模型与代码 | 团队同一、模型确实一致，代价是耦合 |
| 客户-供应商 | 下游提需求，上游按约定提供 | 上下游地位明确，如订单 → 库存 |
| 防腐层 | 下游自己写一层转换，隔离上游模型 | 上游是外部系统或老系统，最常用 |
| 开放主机服务 | 上游提供一套稳定的对外协议供多方使用 | 一个上游对多个下游 |

最该警惕的是**共享内核**。它看起来最省事：两个服务共用一个 `common` 模块，里面放实体类。半年后这个模块会变成所有服务的公共垃圾场，改一行要发布五个服务。共享的应该是**协议与契约**(接口定义、事件结构)，不是实体类。

**跨上下文不共享实体类**是一条硬规矩。订单上下文有自己的 `Order`，库存上下文需要的是「订单号 + SKU + 数量」，给它一个 `StockDeductCmd` 就够了，不需要它认识你的 `Order`。

## 落地顺序

1. **先划边界**，再建模型。边界没定就写实体，后面全是返工；
2. **按上下文分包**，而不是按技术分层包。`com.example.order.domain` / `com.example.stock.domain` 比 `com.example.domain` 里塞所有实体好维护；
3. **上下文之间只走接口与事件**，不走共享实体；
4. **一个上下文内部再分层**(下一篇讲)，别把两层混在一起做。

## 小结

- 一个模型覆盖全系统，会因同一个词多种含义而失真，最终变成没人敢动的巨型类；
- 限界上下文把模型限定在术语唯一、规则自洽的边界内，业务复杂度被隔离而不是被消除；
- 统一语言：业务与代码同一套词，歧义记进术语表并统一；
- 边界按业务能力、团队、语言变化点划；检验标准是「能否独立改一次需求」;
- 上下文之间用共享内核、客户-供应商、防腐层、开放主机服务；共享内核最危险，**不要共享实体类**;
- 先划边界，再建模型；按上下文分包，再在包内分层。
