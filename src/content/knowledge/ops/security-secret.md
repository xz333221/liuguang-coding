凭据管理的目标不是“藏得深”，而是“能审计、能轮换、泄露后能快速失效”。硬编码在代码或配置里的密钥，一旦仓库泄露就无法挽回。

## 凭据分类

| 类型 | 示例 | 保护重点 |
| --- | --- | --- |
| 应用凭据 | 数据库密码、API Key | 最小权限、轮换 |
| 传输凭据 | TLS 私钥 | 文件权限、备份加密 |
| 身份凭据 | SSH 私钥、服务账号 | 不共享、可追溯 |
| 会话令牌 | JWT 签名密钥 | 长度、过期与撤销 |

不同凭据的泄露影响不同，但共同要求是：不进入代码仓库、不写入日志、不通过聊天工具传递。

## 存放方式

- **环境变量**：适合容器与 12-factor 应用，但进程环境可能被同机其他进程读取；
- **受权限保护的文件**：`/etc/app/env`，权限 600，属主为运行用户；
- **密钥管理服务**：Vault、云 KMS、密钥托管，支持审计与动态凭据；
- **编排平台 Secret**：Kubernetes Secret 默认只是 base64，需要配合加密与 RBAC。

小规模从“600 权限文件 + 环境变量注入”起步，规模变大后再引入集中式管理。

## 注入与使用

```bash
set -a
. /etc/app/env
set +a
exec /opt/app/bin/start
```

- 启动时注入，不把凭据写进镜像；
- 镜像构建参数（`ARG`）会留在镜像历史里，不要用；
- 日志与错误信息中过滤密码、令牌；
- 前端代码、移动端包里的密钥一律视为公开。

## 最小权限

- 数据库账号只授权目标库与必要操作；
- 云 API Key 按需授权，避免主账号密钥；
- 服务账号与人员账号分离；
- 不同环境使用不同凭据，测试密钥不能访问生产。

## 轮换

- 制定周期：数据库密码 90 天，API Key 按风险分级；
- 轮换要支持新旧并存，避免切换瞬间全部失败；
- 自动化轮换并记录版本；
- 离职、疑似泄露、权限变更时立即轮换。

## 泄露处置

1. 立即吊销或轮换受影响凭据；
2. 检查访问日志，确认是否被使用；
3. 排查泄露路径（仓库历史、日志、镜像层）；
4. 清理历史记录中的密钥，并通知相关方；
5. 复盘流程，补上检测与权限缺口。

## 常见坑

- **密钥写进 `.env` 并提交**：即使后来删除，历史里仍在；
- **在日志里打印完整配置**：排查方便，泄露也方便；
- **一个密钥多处复用**：一处泄露全部沦陷；
- **轮换没有回滚方案**：新密钥未生效，服务中断；
- **测试环境使用生产密钥**：测试流量污染生产数据。

## 小结

- 凭据不进仓库、不进日志、不进镜像；
- 按影响分级，选择环境变量、权限文件或密钥服务；
- 最小权限与分环境隔离是基础；
- 轮换要支持新旧并存并自动化；
- 泄露后先吊销，再排查路径与影响。
