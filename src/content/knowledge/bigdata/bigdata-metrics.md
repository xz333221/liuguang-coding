“日活是多少”看似简单，实际取决于：按登录还是按访问、是否去重、时区、是否包含测试账号、统计周期。指标治理就是把这些选择固定下来，并让所有人引用同一个定义。

```mermaid
flowchart LR
  A["原子指标: 支付金额"] --> B["派生指标: 日 GMV"]
  B --> C["复合指标: 客单价"]
  D["口径: 时间 / 过滤 / 去重 / 单位"] -.-> A
  D -.-> B
```

## 三层指标

- **原子指标**：不可再拆的业务度量，如支付金额、订单数；
- **派生指标**：原子指标 + 时间 + 维度 + 过滤，如“近 7 天华东地区 GMV”；
- **复合指标**：多个指标运算，如客单价 = GMV / 支付用户数。

原子指标要少而稳定，派生指标按分析场景组合，复合指标在应用层计算。

## 口径要素

一个完整指标定义至少包含：

| 要素 | 说明 |
| --- | --- |
| 业务含义 | 一句话说明度量什么 |
| 统计对象 | 订单、用户、商品还是事件 |
| 时间口径 | 下单时间、支付时间、事件时间 |
| 过滤条件 | 有效订单、排除测试、币种 |
| 去重方式 | 不去重、按用户去重、按订单去重 |
| 单位与精度 | 元/分、百分比小数位 |
| 数据来源 | 哪张 DWD/DWS 表 |

缺少任何一项，不同人算出来就可能不同。

## 指标平台

- 指标定义集中管理，SQL 由模板生成；
- 指标与血缘关联，能追到源表与任务；
- 变更走审批与版本，历史结果可复现；
- 指标 API 供看板、接口与自助分析复用。

没有平台时，至少维护一份指标字典，并让报表引用同一套视图。

## 一致性对账

- 实时与离线按同一时间段对比；
- 新旧口径并行一段时间，确认差异；
- 差异定位到过滤、去重、时间边界或迟到数据；
- 对账结果记录，作为口径变更的依据。

对账不是“数字必须完全相等”，而是“差异可解释”。

## 常见问题

- **同名不同义**：两个团队都叫“活跃用户”，定义不同；
- **时间边界**：自然日与 24 小时、时区差异；
- **去重错误**：按订单去重与按用户去重混用；
- **过滤遗漏**：退款、测试、刷单数据未排除；
- **指标漂移**：SQL 被直接修改，没有版本记录。

## 小结

- 指标由原子、派生与复合三层组成；
- 口径必须写清时间、过滤、去重、单位与来源；
- 指标平台集中定义并关联血缘；
- 实时与离线要定期对账，差异可解释；
- 指标治理的本质是让所有人引用同一个定义。
